Hi Kevin, Oba, Ray,
 
Over the last 2 weeks or so I have observed several gaps relating to FUM initiatives. These include initiatives that are in the pipeline or ready to launch, as well as existing features on Compass. Although I’ve mentioned some of these to you previously, or you’ve been in meetings where they’ve been raised, I wanted to provide you with a consolidated view so that we can work together to determine who should take the lead on these and how they should be prioritised.
 
While this email is long, I have tried to provide sufficient context on each gap, while keeping the details to a minimum. I am happy to dive into the details with you and provide additional context. For most of the gaps, I do have recommendations on how they can be addressed, and in other cases I believe a discussion is warranted to determine the course of action. I have also listed what I consider to be the immediate priorities.
 
EMPLOYEE SSO
1.      CX IIQ implementation
Employee SSO was set to go live on November 3. End-to-end testing was not possible in lower environments due to IIQ limitations. Real testing started in production on October 22, after the IIQ implementation, but were quickly faced with multiple issues: 
•	A key product requirement, which would allow activation to continue to manage unlaunched feature access was excluded in the solution. This would result in alpha, beta and pilot no longer being possible.
•	IIQ was not correctly configured; certain features were still being assigned despite the matrix documenting they should not be.
•	User modifications through IIQ did not work during testing.
•	More comprehensive testing is required. After I asked, it was confirmed that we need to validate all request types coming from IIQ. This means 43 use cases across 3 scenarios, and due to the limited number of people we can test with, we may not have sufficient test coverage
•	While FUM and IT are actively working on resolving the above, we have only until the end of the year to implement and go-live based on the Risk team. I am concerned we may not make this deadline.
 
2.      Datawarehouse (DWH) user setup
It was brought to my attention that Darwin’s team was unable to setup new users on DWH. This one is the result of previous discussions between Product Management and the Data Team.
•	The ability to create DWH users was removed from CX prematurely. The data team has no way to turn on DWH access for users at present.
•	This was done because an interim process was going to be implemented after Employee SSO was launched, that would allow the setup of DWH users to resume. 
•	The interim process would require a user to request for CX access and then DWH via IIQ. Meaning all DWH users would need a CX profile. However, teams who are not configured as part of the CX IIQ, but require DWH access, will not be approved for CX profiles. Today there are ~250 users who have only DWH access but no CX.
•	An agreement was in place for Darwin's team to decouple DWH from CX, which we learned is being prioritized for the end of the year. Until that is done some teams may not be able to get access to DWH.
 
3.      Package Limitations for Operations teams
CX user packages were designed to be finite, with specific feature bundling and permission levels each. They were intended to be used for both clients and employees. To support Employee SSO the matrix was constructed around these packages, to standardize the permissions across each package (through IIQ config not CX).
•	Because of the way these packages were constructed, the limitations of IIQ and the Risk/Security guidelines for employees, we do not have sufficient packages to customize access for speciality teams or ops.
•	To address this, we would need to create new packages for unique cases where some teams need very specific and limited access. This is not sustainable as we already have 27 packages to manage, so scaling with this FUM model is challenging.
 
SECURE ZONE APPLICATIONS
***What I have stated here was also part of the email exchange between Oba and Lamiae***
The launch of SZ applications was intended to be in early December, however, with the gaps that have surfaced (resurfaced in some cases) this will need to be postponed.
 
1.      Supporting Multi-Firm before Multi-Firm is available on CX
In earlier discussions this year, when SZ app migration was prioritized over Multi-Firm it was decided that we would not do any clean-up on ID’s in CX or SZ. Specifically, that we would continue to allow users to have multiple SZ ID’s and those who have a single SZ ID it could be linked to multiple CX ID’s.
•	Through testing being done by Professional Services, it was brought to my attention that linking of a single SZ ID to multiple CX profiles would not be supported. Later confirmed by Delivery and the SZ app migration project team.
•	This meant we would need to either decouple the SZ ID’s based on Firm ID’s or advise clients that only one of their CX ID’s could be used for SZ apps (including Servicing & GIC Management).
•	The three concerns with this are (1) having to force a new temporary behaviour onto clients; (2) recoupling the SZ ID’s once Multi-Firm is available on CX; (3) reassigning iMOST & Servicing recurring requests to the individual decoupled SZ IDs, only to recouple them later when Multi-Firm is available on CX.
 
2.      Undefined End-to-End User Experience
From a simple demo of the CX experience (post app migration), multiple items seemed to still be undefined:
•	Session time-out inconsistency with CX of some apps.
•	In-app menu options that conflict with the idea of single sign-on from CX (i.e. password reset, redirection to welcome page)
•	Log-out & timeout behaviour (where is the client redirected).
•	Experience if a client attempts to access SZ through the direct link.
•	Welcome page behaviour, specifically if iMOST stays on SZ and is not migrated onto CX.
Some, if not all of the above have been discussed in various sessions and meetings over the last year. I had provided feedback and most of the team agreed with my suggestions. It was a surprise to learn that these items remained undefined.
 
PLATFORM NAVIGATION
Any time a new feature is launched it needs to be added to the navigation. The current design does not support a consistent and intuitive experience across all feature groupings.
•	Not all features with sub-feature grouping are treated the same.
•	Onboarding is the most inconsistent, as the behaviour can vary whether a user has 1 or many features assigned within that group. If they have one, clicking Onboarding opens that one feature. If they have multiple, clicking Onboarding opens CRS FATCA and the sub-menu is expanded.
•	The behaviour of “Servicing” when non-trade file uploads is introduced is unknown.
•	Since Servicing is not available in the Employee tenant, it’s unclear how non-trade file uploads will be accessible by employees.
•	This specific navigation gap impacts the following upcoming feature launches:
o	CRS FATCA Submissions
o	Estate Submissions
o	File Uploads (non-trade)
 
ACCESS REQUEST FORM UPDATES
While holding off on the Unified Access Request (UAR) form on CX is essential to focus on Multi-Firm, to launch any new features (i.e. Estate Submissions and File Uploads) the existing user access forms need to be updated. My Request can easily be updated as required. The Unified Access Form on iMOST/Servicing is much harder to get updated, as the team who owns this does not wish to invest in it any further. We also committed to them that after GIC Management we would not request for future updates, anticipating we’d have UAR. While Kevin helped get the Unified Access Form updates prioritized in the past, it is unclear who needs to be creating the requirements and running with these updates. Without updating both these legacy forms, we are unable to launch new features and risk confusing Firm Security Stewards.
 
LAUNCH AND RELEASE ACTIVATION
This one is for awareness only, as I will be sending Sujith and Esther an email. This past weekend it took me 8 hours to enable Client Documents for 10K users, some requiring re-upload because the system timed out while the files were loading. This is a performance issue, which was already raised earlier this year. We were told that performance has improved and even requested to validate in pre-prod (where it appeared ok). We cannot continue to launch features without performance improvements and additional tools (i.e. Firm level activation not just user).

Based on my understanding of the initiatives and the criticality of each, I suggest we focus on the following 3 as their impact is immediate and material.
1.      Employee SSO - Datawarehouse (DWH) user setup
2.      Secure Zone Applications
3.      Platform Navigation – Onboarding behaviour of CRS FATCA
 
I hope this has given you a broader view of the gaps I’ve observed. I suggest we set up time to go through these to align on significance, prioritization, and ownership of each.
