Multi-firm: design model, sequences and the access equation

Built from the clickable walkthrough (one person, several profiles, two kinds of relationship record). Nothing here depends on choosing one or two logins — the model supports both; the sequences show the one-login path and note where two logins differ.

1 · Design model

Thirteen things, four of them new: FirmRelationship (parent/child and delegation in one table), Assignment (the “profile” in the mock-up — a person working for a firm in a given role), Bundle (the feature ceiling a relationship allows) and RRGrant (data scope with the relationship it came through). Everything else already exists in some form.

Read it from the person outwards: a person holds assignments; each assignment has a firm context, a user package, RR grants and its own Secured Zone IDs. Relationships between firms decide which contexts a steward may offer and what each one may contain.

The rules the model enforces

RuleWhere it lives
A person exists oncePerson; logins and assignments hang off it, so attestation and offboarding see one record
Features depend on where you are workingUserPackage is on the Assignment, not on the Person or the Login
Hierarchy is one level deepFirm.parentCode; a child of a child is not representable, by design
You can only be given what the relationship allowsFirmRelationship → Bundle: OWN and PARENT_CHILD allow everything the firm subscribed to; SUB_ADVISORY allows the trading bundle; REFERRAL allows viewing
You can only reach the accounts the relationship lendsRRGrant.ownerFirm must be the assignment’s firm, a child of it (PARENT), or inside a delegation’s rrScope (DELEGATED)
Access ends with the agreementFirmRelationship.status / end date; delegated grants are removed when it ends
Legacy IDs are linked, not mergedLinkedId: SZ per assignment (per firm), R2 one per person, until each retires
Changes arrive only through requestsAccessRequest is the only writer of assignments; its checklist gates completion on the IDs being linked

3 · The access equation

Today a login is checked against the firm’s package and the user’s package — both must allow the feature (an intersection, not a union) — and the user’s RR codes all sit inside the one firm the login belongs to.

Todayallowed(user, feature) = feature ∈ FirmPackage(firm(user)) ∩ UserPackage(user) reach(user) = RR codes assigned, all inside firm(user)

Multi-firm adds two things: the check is made for a context (an assignment) rather than for the login, and the feature must also be allowed by the relationship between that context and the firm that owns the account.

Multi-firmallowed(person, context, feature, account) = feature ∈ Package(context) -- what the steward ticked ∩ FirmPackage(firm(account)) -- what the account’s firm subscribed to ∩ Bundle(relationship(context, firm(account))) -- what the relationship permits AND RR(account) ∈ Grants(context) -- the account is in the context’s scope AND relationship(context, firm(account)).status = ACTIVE

where relationship() is OWN when the account’s firm is the context’s firm, PARENT_CHILD when it is a child of it, and the delegation record when the account came through a delegation. Bundle(OWN) and Bundle(PARENT_CHILD) are “everything”, so for a normal user the three-way intersection collapses to today’s two-way one — single-firm clients see no change.

How the context is chosen — the only difference between the options

Optioncontext =What must change
A · two loginsthe login itself (each login is one assignment)Nothing in the apps; FUM links both logins to one person
B · one login, switchthe assignment the person selected in the switcher, carried in the sessionFUM resolves per (person, context); session carries the context; apps that cache features per user
C · one login, by accountthe assignment whose relationship covers firm(account), chosen per requestEvery app evaluates per account; mixed lists must mask fields row by row

The equation is identical in all three; A and B fix the context for the whole session, C evaluates it per account.

4 · Does the design cover the thirteen pain points?

Eleven fully, two with a condition. None is outside the model.

PainCoveredHow, and what the model does not do by itself
Many logins for one personyesOne person, one login (two in the interim option); firms and systems hang off assignments. Secured Zone IDs are linked to the assignment and passed as SSO context, so they stop being logins the person types.
No single view of the groupyesA PARENT assignment with RR grants from the children gives one context over the group. Apps still have to build the aggregate views (Accounts, Orders); Servicing already aggregates.
Set up as someone else’s employeeyesThe DELEGATED assignment lives in the home firm and points at FirmRelationship records; the delegating firm never creates the person.
A request for every firmyesOne request creates or changes one assignment for the whole context (parent group or delegated slice). Behind the scenes the SAA still provisions SZ and R2 per firm until those retire — the steward no longer sees that.
Moving within the group means starting overyesA Modify re-points the assignment’s firmContext or RR grants; the person and the login stay. Re-parenting a firm (Cumberland) changes FirmRelationship rows, not people. Transition rules for RR grants when a child leaves a parent still need writing.
Switching all daywith a conditionOne credential, and the switch is a context switch inside Compass instead of a new login. A sub-advisor still switches between home and delegated books unless the account-derived option (C) is built.
Operations do the advisors’ workyesSolved by reach: the parent or delegated assignment carries the RR grants the person actually needs, so the task can be done from their own identity. Needs the grants to be set up correctly — a process point, not a model gap.
Attestation is a reconciliation choreyesAttestation is per person with one item per assignment; delegating firms confirm the relationship, not the individual. The attestation module itself is a later build; the model carries what it needs.
Offboarding leaksyesDeactivate the person → every assignment, RR grant and linked ID goes with it. End a delegation → only that assignment’s grants go.
Workarounds the firms end up owningyesRR grants are validated against FirmRelationship (parentCode or delegation rrScope), so the hacks are no longer needed — and no longer possible. The existing hacked data must be migrated or cleaned; the model does not do that by itself.
Partners look like staffyesFirmRelationship kind = REFERRAL with the view-only Bundle; the person holds a DELEGATED assignment, visibly a partner, ended with the agreement.
Buying a feature in the wrong placewith a conditionThe equation resolves a feature per account’s firm, so a parent user gets Research on accounts of the firm that bought it. Whether the parent user may use Research on every child’s accounts is a commercial rule (Penny: everything, bill by metering) that the model can express either way — it is a decision, not a gap.
Stuck on legacy for tradingyesThe DELEGATED assignment with the trading Bundle is exactly what Compass trading needs to accept Nora’s delegated orders. NetRep can then retire for sub-advisors; SZ apps get the right SZ context; R2 is unchanged until its sunset.

Three things sit next to the model rather than inside it, and all three were raised on the call: the migration of today’s hacked data (sibling RR codes in R2’s sub-advisor field, cross-firm codes in SZ), the Secured Zone and firm-user clean-up, and the Firm360 feed that keeps FirmRelationship current. Without them the model is correct and the data is not.
