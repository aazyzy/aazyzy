What this proposes, in one page

All groups

Keep today’s architecture, add two things

Keep the 27 packages, the matrix, ID Admin provisioning by hand, Secured Zone IDs and R2 IDs. Add a parent group that a Compass user can belong to, and one request form inside Compass that carries firm context. No feature registry, no system integration layer, no automated provisioning. Sub-advisory access follows with trading.

Why

Multi-firm firms cannot launch without a way to request access under the new model. The registry and system integration were the largest part of the six-month estimate and are not needed to request or provision a parent group user. Everything else is form, status and checklist work on top of screens and tools that already exist.

In scope for v1

Parent group firm type and child-firm list · request form (create, update, deactivate) with firm scope, package-first access, RR codes per firm, system checkboxes · steward status page · ID Admin queue with Firm360 check and matrix-linked checklist · one-time credential · retire after first sign-in · one row per person in the steward’s user list.

Out of scope for v1

Feature registry, system integration registry, machine-generated instructions, automated provisioning, sub-advisory access (phase 2 with trading), self-serve user management, attestation, the R2 decommission slice (second half of 2027).

What must change, and what stays

Must change
  1. Parent group as a firm type with a child-firms list (Firm360 Parent_Code; manual row until the loader carries it).
  2. A user may belong to a parent firm; RR validation uses the union of child ranges.
  3. One global parent package; modules that cannot run across firms stay child-only.
  4. Steward designation stored on the firm.
  5. Access Requests module: form, status list, ID Admin queue, checklist, one-time credential.
  6. Duplicate-ID lookup by email at intake.
  7. First-sign-in event used to unblock the retire step.
  8. Request screens placed in an FSS-assignable package (Product Activation task).
Stays exactly as today
  • The 27 user packages and the firm-package intersection rule.
  • Radhika’s matrix and ID Admin provisioning by hand.
  • Compass user management screens and the bulk upload tool.
  • Okta identity model.
  • Secured Zone Security App and existing SZ IDs — nothing decoupled.
  • NetRep legacy request form.
  • R2 IDs per firm, linked for audit, until R2 functions move to Compass.
  • No feature registry, no system integration layer, no machine-generated instructions.
