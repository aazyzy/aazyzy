2. What the package header means

  "packageTemplateId": 66,
  "name": "ManageOrders_V1.17",
  "description": "ManageOrders",
  "type": "User",
  "firmType": "NBIN",
  "active": true

Plain English: This is active user package 66, called ManageOrders, intended for NBIN users.

3. The details are what the package contains

A package detail pointing to resource 133, client_accounts, means the ManageOrders package includes the Client Accounts capability. Other details may include Orders View, Positions, Transactions, Reports and tools.

4. Assignment type inside these JSON files

In the JSON package definitions, resource-side entries commonly use assignmentType S, while the package’s user-group entry uses assignmentType G. Operationally, S identifies resource/feature-side package details and G identifies a userGroup. The formal expansion of S still requires confirmation.

5. Assignment mode M versus O

Value | Observed pattern         | Simple working meaning
M     | selectionDefault = true  | Included/default component of the package
O     | selectionDefault = false | Optional/selectable component of the package

6. Resource versus feature

A resource is the thing being controlled, such as Orders Module, Client Accounts or Positions. A feature is the business capability available on that resource, such as View Orders or Manage Mutual Fund Uploads. A useful memory aid is: Resource = WHAT exists; Feature = WHAT YOU CAN DO with it.

7. User groups

Packages can also contain a technical group such as Wealth.CompassX.ManageOrders. The group is one mechanism through which technical access can be delivered or enforced.

8. Why there are many files

Each file defines a different access bundle, such as Manage Orders, Manage Service Requests, Manage Firm and User, Manage All, Admin All or Global Admin.

9. Supermarket analogy

Resources/features are individual products. A package is a pre-built shopping basket. Instead of giving Ali each product separately, FUM assigns one basket containing the required products.

10. How this relates to P/R

There are two layers. At the user-assignment layer, P/R appears to say whether the user receives a package or a direct resource. Inside the package definition, S/G says whether a package detail is a resource/feature-side item or a user group. These are not contradictory because they describe different levels.

USER -> ASSIGNMENT -> PACKAGE
                         +-- S: resource/feature items
                         +-- G: technical user group

USER -> ASSIGNMENT -> direct RESOURCE

MICROSOFT COPILOT
The database structure makes the model clearer. The main source of confusion is that “assignment” is used at two different levels.

The simplest model

USER -> receives an ASSIGNMENT -> PACKAGE -> contains RESOURCES / FEATURES -> connected to PERMISSIONS

In business language: A user receives a package. The package contains features and resources that determine what the user can use. Permissions describe the allowed actions.

1. User
USER_CONFIGURATION answers “Who is this user?” It stores name, username, email, status, identity-provider data, OSS ID, preferred module, last login and access-profile status. IDP_SUBJECT is the stable identity key used to connect the user to assignments.

2. Package
PACKAGE_TEMPLATE defines the reusable access box. Important columns include PACKAGE_TEMPLATE_ID, NAME, DESCRIPTION, TYPE, FIRM_TYPE and ACTIVE.

3. Package details
PACKAGE_TEMPLATE_DETAILS defines what is inside the box using PACKAGE_TEMPLATE_ID, ASSIGNMENT_TYPE, ASSIGNEE_ID, ASSIGNMENT_MODE and SELECTION_DEFAULT.

4. Two assignment-type systems
USER_ASSIGNMENT uses USER_ASSN_TYPE and answers what was assigned to a particular user. The working interpretation is P = Package and R = Resource. PACKAGE_TEMPLATE_DETAILS uses PKG_ASSN_TYPE and describes what is included inside a package. The package JSONs show S for resource/feature-side details and G for user groups.

5. Feature package
FEATURE_PACKAGE is a versioned package record tied back to PACKAGE_TEMPLATE. Think of PACKAGE_TEMPLATE as the definition and FEATURE_PACKAGE as a specific active version or instance.

6. Resource and feature
RESOURCE is the technical umbrella object. The table contains RESOURCE_ID, NAME, DESCRIPTION, GROUP_NAME, TYPE, VERSION, CONF_URI, ACTIVE, LABEL, PURPOSE and RESTRICTION. A feature appears to be represented as a classification or purpose of a RESOURCE rather than as a separate core table.

7. Permission
PERMISSION defines an action or capability. PERMISSION_ASSIGNMENT connects a PERMISSION_ID to a RESOURCE_ID. A useful formula is RESOURCE + PERMISSION = CAPABILITY.

8. Role and group
ROLE groups permissions through ROLE_ASSIGNMENT. USER_GROUP connects to roles through USER_GROUP_ASSIGNMENT. This provides a group -> role -> permission delivery path.

9. Complete relationship

USER_CONFIGURATION
   -> USER_ASSIGNMENT
      -> P: PACKAGE_TEMPLATE
          -> PACKAGE_TEMPLATE_DETAILS
             -> S: RESOURCE -> PERMISSION_ASSIGNMENT -> PERMISSION
             -> G: USER_GROUP -> USER_GROUP_ASSIGNMENT -> ROLE -> ROLE_ASSIGNMENT -> PERMISSION
      -> R: RESOURCE directly

10. Realistic example
User abc-123 receives package 66. Package 66 is ManageOrders. Its package details point to Orders Module, Orders View, Equity Product and a ManageOrders group. Permissions and roles then support enforcement. The result is that the user receives the order-management capabilities represented by that package.

Simple picture

USER
  -> USER_ASSIGNMENT
      +-- P -> whole package
      |          -> PACKAGE_TEMPLATE_DETAILS
      |              +-- S -> resource/feature item
      |              +-- G -> user group
      +-- R -> individual resource directly

Recommended trace order

1. USER_CONFIGURATION: Find the user and obtain IDP_SUBJECT.
2. USER_ASSIGNMENT: Find all objects assigned to the user.
3A. PACKAGE_TEMPLATE: Resolve P assignments.
3B. RESOURCE: Resolve R assignments.
4. FEATURE_PACKAGE: Check active package version.
5. PACKAGE_TEMPLATE_DETAILS: Expand package contents.
6A. RESOURCE: Resolve S details.
6B. USER_GROUP: Resolve G details.
7. PERMISSION_ASSIGNMENT: Find permissions linked to resources.
8. PERMISSION: Understand the action/capability.
9. USER_GROUP_ASSIGNMENT: Find roles linked to groups.
10. ROLE: Identify the role.
11. ROLE_ASSIGNMENT: Find permissions linked to the role.

Practical checklist

1. Find the user by email or username.
2. Copy IDP_SUBJECT.
3. Search USER_ASSIGNMENT by IDP_SUBJECT.
4. Separate P and R results.
5. For P, resolve the package and expand its S and G details.
6. For R, resolve the resource directly.
7. Follow resource -> permission and group -> role -> permission.
8. Check effective/expiry dates and ACTIVE flags.
9. Check firm scope separately.

Important: because ASSIGNEE_ID is polymorphic, read ASSIGNMENT_TYPE before choosing the target table. Do not join the same numeric ID indiscriminately to all possible tables.

What the screenshot is proposing
The UI represents scoped RBAC with per-user overrides. The selected role supplies baseline feature-level access. An administrator can add or remove a specific level, apply firm/RR/parent scope, observe NBIN-only constraints, enforce dependencies and account for firm subscription.

What already exists
- USER_CONFIGURATION provides the subject.
- PACKAGE_TEMPLATE and FEATURE_PACKAGE provide reusable bundles.
- PACKAGE_TEMPLATE_DETAILS provides package contents.
- RESOURCE can represent modules and features.
- PERMISSION and PERMISSION_ASSIGNMENT represent action levels.
- ROLE, ROLE_ASSIGNMENT, USER_GROUP and USER_GROUP_ASSIGNMENT provide an RBAC foundation.

Main structural issue
The UI needs a three-part relationship: ROLE -> FEATURE/RESOURCE -> LEVEL/PERMISSION. A role should map to a resource-permission pair, not merely to a permission.

Recommended ROLE_ENTITLEMENT
  ROLE_ENTITLEMENT_ID
  ROLE_ID
  RESOURCE_ID
  PERMISSION_ID
  DEFAULT_SELECTED
  ACTIVE
  VALID_FROM / VALID_TO

User additions and removals
The UI’s “added as an extra” and “removed for this person” states require a user-specific entitlement record with RESOURCE_ID, PERMISSION_ID and an explicit ALLOW or DENY effect.

Scope, constraints and dependencies
Firm, RR-code and parent scope should attach to the entitlement decision, not only to the user. NBIN-only restrictions need explicit constraint records. Dependencies such as Mutual Funds Manage requiring Orders View need an entitlement-dependency relationship.

Firm subscription
Subscription availability is separate from authorization. Effective access should combine role/user authorization with firm eligibility.

Effective access = role entitlement + user additions - user removals
                   intersect firm subscription
                   intersect scope
                   intersect constraints and dependencies

Minimum robust extensions
- USER_ROLE_ASSIGNMENT
- ROLE_ENTITLEMENT
- USER_ENTITLEMENT_OVERRIDE
- ENTITLEMENT_SCOPE
- ENTITLEMENT_CONSTRAINT
- ENTITLEMENT_DEPENDENCY
- FIRM_ENTITLEMENT or an equivalent subscription derivation
- Role/versioning support

Recommendation: keep the existing package/resource/permission model as the entitlement catalog, but add a policy layer for role, scope, overrides, constraints and dependencies.

this new model is still RBAC or policy based model? pivot to which one more?

MICROSOFT COPILOT
The proposed model is still RBAC at its core, but it is pivoting toward a policy-based hybrid. A precise label is “scoped, policy-enhanced RBAC.”

Roles remain the human-manageable starting point. Policies determine where, when and under which conditions role-based access is effective.

Element                         | Classification   | Reason
Head-office operations role     | RBAC             | Role supplies baseline access
View/Manage/Control/Process      | RBAC             | Permissions can be assigned through the role
Added as an extra               | Policy/exception | User-specific grant changes role baseline
Removed for this person         | Policy/exception | Explicit deny changes inherited access
Firm/RR/parent scope            | Policy           | Access depends on target context
NBIN only                       | Policy           | Access depends on user/firm attributes
Firm subscription               | Policy           | Eligibility condition
Feature dependency              | Policy           | Decision depends on another entitlement
Validity dates/status           | Policy           | Decision depends on time/state

Recommended pivot
Do not move to pure PBAC. Pivot from package-centric RBAC to granular scoped RBAC supported by policy evaluation.

RBAC layer: What access normally belongs to the job?
Policy layer: When and where is that access valid?

A concise architecture statement is: FUM uses role-based access control to define reusable business-access baselines. Effective access is determined through policy evaluation using firm scope, RR-code scope, parent hierarchy, firm subscription, entitlement constraints, dependencies, user overrides and assignment validity.

Memory aid: Roles define what; policies determine where, when and under which conditions.

FUM in One Page: A Beginner’s Guide

FUM becomes confusing because package, feature, resource, assignment, permission, user package and firm package describe different layers of the same access model. The easiest question is: Who gets access to what, for which firm, and how is that access delivered?

1. Big picture

FUM
  +-- USER ACCESS: What can a person do? -> User Package
  +-- FIRM ACCESS: What has a firm subscribed to? -> Firm Package
                              |
                        Effective Access

Simple rule: the user must have permission AND the firm must have the capability/subscription.

2. Main objects

Term         | Simple explanation                         | Analogy
User         | Person receiving access                    | Employee
Firm         | Organization whose data is accessed        | Branch/client organization
Resource     | One technical access item                  | One key
Feature      | Business function                          | Room the key opens
Permission   | Action allowed                             | View, Manage, Control, Process
Package      | Reusable bundle                            | Box of keys
User package | Package assigned to a person               | Job-access kit
Firm package | Package assigned to a firm                 | Services purchased
Assignment   | Connection saying access was given         | Handover record
Role         | Business responsibility grouping access   | Order Manager
Group        | Technical delivery/enforcement group       | Security group
Scope        | Where access is valid                      | Firm/RR/parent-child

3. Package, resource, feature and permission
Package = the box. Resource = one technical item inside the box. Feature = the business-friendly function. Permission = what action the person may perform.

Manage Orders Package
  +-- Orders module
  +-- View orders
  +-- Manage mutual funds
  +-- Manage equity orders
  +-- View reports

A useful formula is Resource + Permission = Capability.

4. User package versus firm package
A user package answers “What is this person allowed to do?” A firm package answers “What products or capabilities are available to this firm?” Both sides must align for effective access.

Alex -> Manage Orders user package
ABC Wealth -> Orders firm subscription
Both true -> Alex can manage Orders for ABC Wealth

5. Assignment
An assignment is the relationship record connecting a user or firm to an access object. At the user level, P indicates a package assignment and R indicates a direct resource assignment under the current working interpretation.

6. Inside a package
PACKAGE_TEMPLATE defines the box. PACKAGE_TEMPLATE_DETAILS defines the contents. Inside the details, S identifies resource/feature-side items and G identifies a user group in the observed package JSON files.

7. End-to-end example
1. Alex exists in USER_CONFIGURATION.
2. Alex is assigned the Manage Orders user package.
3. The package expands into Orders Module, Orders View, Mutual Funds, Equity and a ManageOrders group.
4. Permissions define allowed actions.
5. Firm subscriptions determine where those actions are available.

8. Complete FUM flow

USER -> ASSIGNMENT -> USER PACKAGE -> RESOURCES / FEATURES -> PERMISSIONS
                                                   |
                                              FIRM PACKAGE
                                                   |
                                           EFFECTIVE ACCESS

9. UI/UX questions
- Who are we configuring?
- For which firm?
- What job/role/package?
- What functions come with it?
- What can the person do?
- Is the firm eligible?
- Where is access valid?
- Is this standard access or an exception?
- When does it start/end?
- Why does access exist?

10. Five sentences to remember
1. A user is the person receiving access.
2. A package is a reusable box containing access items.
3. A resource is one technical access item; a feature is its business-facing meaning.
4. A permission describes the action allowed.
5. Effective access exists only when the user is allowed and the firm is eligible.

WHO? User | WHAT BOX? Package | WHAT ITEM? Resource/Feature | WHAT CAN? Permission | WHERE? Scope | WHY? Assignment | RESULT? Effective access
